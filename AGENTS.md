# AGENTS.md — orbit-web

Инструкции для AI-агентов (Claude Code, Codex, Cursor и др.) и для людей.

Orbit — открытое приложение с постоянными голосовыми комнатами для команд и сообществ.
Этот репозиторий — web-клиент. API-сервер — отдельный репозиторий `orbit-server`.
Источник требований — PRD 3.1 (Orbit — PRD 3.0 в Claude Docs). Текущий этап — spike: голос и экран в браузере.

## Команды

```bash
pnpm install
pnpm dev          # http://localhost:5173, нужен .env.local (cp .env.example .env.local)
pnpm check        # typecheck + lint + lint:fsd + format:check + test — запускай перед тем, как считать задачу готовой
pnpm lint:fix && pnpm format   # автоисправления
pnpm test         # Vitest; один файл: pnpm vitest run src/shared/ui/button
pnpm test:e2e     # Playwright против живых orbit-server + LiveKit (make up && make run в orbit-server)
pnpm test:e2e:cross-browser  # тот же смоук в Chromium и WebKit (Safari); нужен `playwright install`
pnpm test:e2e:pwa # сборка + preview на 4173: манифест и офлайн-оболочка
```

Node 22+, pnpm 11. Не используй npm или yarn — lockfile только `pnpm-lock.yaml`.

## Стек

React 19, TypeScript (strict, `noUncheckedIndexedAccess`), Vite 8, React Router, Radix UI (`radix-ui`),
Tailwind CSS 4, `class-variance-authority`, TanStack Query, TanStack Virtual, React Hook Form,
Vitest + Testing Library. Медиа — `livekit-client`. По PRD позже добавится Zustand — не тащи другие аналоги.

Не добавляй: Material UI и любой CSS-in-JS (Emotion, styled-components), Redux, axios, moment, lodash целиком.
Новая зависимость — только если без неё никак; решение уровня стека фиксируй в `docs/adr/`.

## Архитектура: Feature-Sliced Design

```
src/app       → entrypoint, routes, styles
src/pages     → страницы, слайс = маршрут
src/widgets   → крупные блоки UI
src/features  → действия пользователя
src/entities  → бизнес-сущности
src/shared    → ui, lib, api, config — без бизнес-логики
```

Правила проверяются линтером (`eslint-plugin-boundaries`, `no-restricted-imports`, Steiger). Не отключай их.

- Слой импортирует только слои ниже. Слайсы одного слоя не импортируют друг друга.
- Слайс экспортирует публичный API через `index.ts`; снаружи — только `@/features/<slice>`.
- `shared` — до модуля сегмента: `@/shared/ui/button`, `@/shared/lib/cn`.
- Между слоями — алиас `@/`, внутри слайса — относительные пути.
- Сегменты называются по назначению: `ui`, `model`, `api`, `lib`, `config`. Не `components`, `hooks`, `utils`, `types`.
- Нужно что-то общее двум фичам — опусти в `entities` или `shared`, а не импортируй фичу из фичи.

## Код

- Экспорты именованные (`import-x/no-default-export`). Исключение — страницы: `pages/*/ui/*Page.tsx` и
  `pages/*/index.ts` экспортируют страницу только по умолчанию (`export default LoginPage`,
  `export { default } from './ui/LoginPage'`), роутер берёт её так же и в `lazy()`. Плюс конфиги инструментов.
- Компоненты — стрелочные функции (`export const Button = () => …`), и всё, что объявлено внутри
  компонента, — тоже (`const handleSubmit = () => …`). В `.tsx` `function`-объявлений нет вообще:
  это проверяют `react/function-component-definition` и `func-style`. Файл компонента в PascalCase
  (`Button.tsx`), тест рядом (`Button.test.tsx`).
- Формы — React Hook Form: `useForm` + `register`, проверки в правилах `register` (`required`,
  `minLength`, `validate`), отправка через `handleSubmit`. Не заводи `useState` на каждое поле. Значение
  поля для отрисовки — `useWatch`, а не `watch()`: с `watch` React Compiler пропускает компонент. Свой
  `ref` на поле совмещай с `register(...).ref` в одном callback-ref. Состояние не формы (открыт ли
  попап, где каретка) остаётся в `useState`.
- Тело `if`, `else`, циклов — всегда в фигурных скобках, даже одна строка: `if (x) return` в одну строку
  не пишем (`curly: all` в ESLint, `pnpm lint:fix` расставит сам).
- `import type` для типов. Без `any`, без `as` ради обхода типов, без `// @ts-ignore` и `eslint-disable`.
- Обращения к ОС и браузерным API (уведомления, устройства, захват экрана, автозапуск) — только через
  `getPlatform()` из `@/shared/platform` (`PlatformAdapter`). Компоненты не вызывают Tauri и браузерные API
  напрямую (PRD 11.0), это проверяет ESLint. Что остаётся внутри livekit-client — `docs/adr/0004-platform-adapter.md`.
- Переменные окружения — только через `@/shared/config`; новые описываются в `src/vite-env.d.ts`, `.env.example`
  и `.env.test` (значения для Vitest и CI).
- API orbit-server генерируется из `api/orbit-server.openapi.yaml` (Hey API) в `src/shared/api/generated/`
  перед `dev`, `build`, `typecheck`, `lint` и `test`. Сгенерированное не коммитится и не правится руками.
- Запросы — только через `@/shared/api`: `useQuery(getReadinessOptions())`, `useMutation(createVoiceTokenMutation())`.
  Не пиши `fetch`, типы ответов и query keys вручную; не импортируй `shared/api/generated` напрямую.
- Все ошибки запросов — `ApiError` (`status: 0` — нет сети, `error.code` — код сервера).
- API изменился на сервере → `pnpm api:pull` (из `main`, ветки или локального пути) и закоммить новый снимок.
- Workflow `API drift` сверяет снимок с `main` orbit-server (еженедельно, вручную, в PR — без блокировки); упал — `pnpm api:pull`.
- Серверное состояние — TanStack Query; не дублируй его в локальном стейте.

## UI и стили

- Компоненты ui-kit — в `shared/ui/<name>/` на примитивах Radix, варианты через `cva`, классы объединяются `cn()`.
- Цвета и шрифты — только токены из `@theme` в `src/app/styles/index.css` (`bg-surface`, `text-fg-muted`).
  Не пиши сырые цвета (`bg-[#123]`, `text-gray-500`).
- Доступность обязательна: `jsx-a11y` в линтере, у интерактивных элементов есть доступное имя, фокус виден.
- Иконки — `shared/ui/icon` (24×24, stroke 2, `aria-hidden`). Кнопка-иконка — `IconButton` из
  `shared/ui/icon-button`: обязательный `label` (идёт в `aria-label` и Tooltip), варианты `ghost | subtle | danger`,
  размеры `sm | md`, `pressed` для тогглов. Текстовая кнопка остаётся там, где слово яснее картинки.
- Тост — `shared/ui/toast`: `useToast()` под `ToastProvider` (он смонтирован в `App` и в `renderWithProviders`).
- Раскладка — три колонки: серверы 64px, каналы 256px, канал, участники 240px. Корень — `h-dvh overflow-hidden`,
  у каждой колонки свой скролл; документ не прокручивается никогда.
- Панели — `rounded-panel`, поповеры — `shadow-popover`; переходы 150 мс, `prefers-reduced-motion` гасит
  анимации в `@layer base`.
- Тексты интерфейса — на русском.

## Тесты

Каждая функция — с тестами. Тестируй поведение через роли и тексты (`getByRole`), а не детали реализации.
Компоненты с запросами рендери через `renderWithProviders` из `@/shared/lib/test`; `fetch` подменяй `vi.stubGlobal`,
`livekit-client` — фейковым `FakeRoom` из `@/shared/lib/test` через `vi.mock`, платформу — `setPlatform(createFakePlatform())`
и `setPlatform(null)` в `afterEach` (пример — `features/share-screen/ui/ShareScreen.test.tsx`).
Сценарии с медиа проверяй в `e2e/` (Playwright, фейковый микрофон): юнит-тест не докажет, что звук доходит.
Общие шаги e2e (канал через меню сервера, инвайт, выход) — в `e2e/helpers.ts`; относительный импорт пиши
с расширением (`./helpers.ts`), этого требует `tsconfig.node.json`.
`e2e/visual.spec.ts` держит визуальные снимки четырёх экранов и axe-проверку (`@axe-core/playwright`,
только `serious`/`critical`). Базлайны сняты на macOS: на другой ОС снимки пропускаются — перезапиши их
через `--update-snapshots` на своей платформе.
`pnpm test:e2e:cross-browser` (`playwright.cross-browser.config.ts`) гоняет один смоук в Chromium и
WebKit; проект `firefox` там есть, но Playwright Nightly 157 не стартует на macOS 27 (падает на
профиле), поэтому Firefox проверяется отдельным запуском на машине, где он запускается.

## Аккаунты и сессии

Сессия живёт в cookie `orbit_session` (HttpOnly), поэтому запросы идут с `credentials: 'include'`
(`shared/api/client-config.ts`), а кто вошёл — знает только сервер: `useSession()` из
`entities/session` спрашивает `GET /auth/me`. Маршруты за `RequireSession` (`app/routes`) ждут первого
ответа и только потом решают, пускать или вести на `/login`. Ответ 401 на любом запросе чистит кеш
TanStack Query и сбрасывает сессию (`shared/api/query-client.ts`), после чего guard уводит на вход.
Отдельной страницы комнаты больше нет: голос живёт в голосовых каналах сервера, и токен выдаётся
по сессии для конкретного канала.

## Оболочка и живой поток

`widgets/app-shell` — рамка для всех страниц с сессией: рельса серверов (64px), колонка каналов (256px),
канал в середине; участники — четвёртая колонка из `widgets/member-list` (240px, на узком экране —
выезжающая панель). Участники сгруппированы как в Discord: каждый — под своей высшей ролью с «показывать
отдельно» (`groupRoleOf`), остальные — «Участники»; ник в колонке и в ленте окрашен цветом высшей роли с
цветом (`colorRoleOf`). Маршруты `/s/:workspaceId/:channelId`, а также `/new` и `/s/:workspaceId/settings`.

Шапка каналов — `WorkspaceMenu`: имя сервера и меню «Пригласить людей», «Создать канал», «Участники и баны»,
«Настройки сервера». Кнопок этих действий в сайдбаре нет. Каналы сгруппированы в «Текстовые» и «Голосовые»;
группы сворачиваются и помнят это в localStorage, у строки на hover/focus — приглашение и настройки канала
(`features/edit-channel`: вкладка «Общее» — имя, тема, «пишут только администраторы», удаление; вкладка
«Права» — переопределения по ролям: для каждого права канала «Запретить / Как на сервере / Разрешить»,
@everyone первой; чужое право и роль не ниже своей заблокированы). Обе панели на < 1024px —
выезжающие поверх чата, Esc и клик по фону закрывают; кнопка «Каналы» живёт в левом верхнем углу.

Внизу колонки — `VoicePanel` и `UserPanel`. `UserPanel`: аватар с точкой связи, ник, бейдж «гость»,
микрофон и звук (с шевронами быстрого выбора устройств), настройки пользователя. Настройки — диалог
`UserSettings` с вкладками «Профиль», «Голос и видео», «Уведомления», «Приложение», «Аккаунт»; выход и
создание аккаунта гостя живут там, а не в сайдбаре. Mute и deafen работают до входа в голос: выбор хранится на
устройстве и применяется при подключении. Горячие клавиши Ctrl+Shift+M и Ctrl+Shift+D — `useVoiceShortcuts`.

Одно WebSocket-соединение на всё приложение держит
`entities/live` (`LiveProvider` над роутером, `useLive()` внутри): смена канала и сервера — это только
новый кадр `subscribe`, сокет не пересоздаётся, а после обрыва соединение возвращается само и повторяет
последнюю подписку. Поток открывается только при живой сессии: без cookie он собирал бы 401.
Всё, что случилось за время обрыва, не приходит: докат по курсору повторяет только новые сообщения.
Поэтому каждое переподключение (не первое подключение) вызывает `refreshAfterGap` — он помечает
устаревшим всё, что обычно обновляют события (`LIVE_QUERIES` в `apply-event.ts`); новый запрос, который
живёт на событиях, добавляй туда же. Новое событие сервера добавляй в `SERVER_EVENTS`
(`event-coverage.test.ts`): тест проверяет, что `applyEvent` что-то с ним делает. Кадр ошибки `behind` (сервер перестал слать события подписки, но
сокет не закрыл) клиент лечит так же — сам закрывает сокет и переподключается.
События не несут данных в стор — они помечают запросы TanStack Query устаревшими, источник правды один.
Кнопки следуют правам с сервера (раздел «Роли и права»), но это удобство: сервер проверяет права заново
на каждом действии. Смена имени, иконки или прав приходит событием `workspace.updated`, а ролей —
`roles.changed`; оба гасят нужные ключи, поэтому кнопки у всех перерисовываются без перезагрузки.

## Роли и права

Модель как в Discord: у участника сколько угодно ролей, права складываются, роли упорядочены, у каждого
сервера есть @everyone. Правила считает сервер (orbit-server, `internal/perms`, README «Роли и права»);
клиент только читает результат.

- **Права на сервере** — `Membership.permissions`; спрашивай `hasPermission(membership, 'kickMembers')`
  (`administrator` даёт всё). Старый `can(membership, 'canInvite')` остаётся для флагов @everyone.
  Не сравнивай `role === 'admin'`: `role` в API выводится из `administrator` для старых клиентов.
- **Права в канале** — `Channel.permissions`, с переопределениями; спрашивай `channelAllows(channel,
'manageMessages', fallback)` из `entities/channel`. Закрытого канала клиент просто не получает.
- **Иерархия** — `rankOf`, `outranks` (`entities/workspace`): действовать можно над теми, чья высшая роль
  ниже, и только с ролями ниже своей; владелец выше всех. Включить можно только право, которое есть у
  самого читателя. Недоступное показывается заблокированным, а не прячется.
- **Где что живёт:** роли сервера — «Роли» в настройках сервера (`RolesSettings`), выдача — `MemberRoles`
  в карточке участника, переопределения — вкладка «Права» в настройках канала (`ChannelOverrides`),
  группы и цвет ника — `groupRoleOf` / `colorRoleOf`. Тексты прав — `PERMISSION_GROUPS`.
- **Колонка участников** — один плоский список с заголовками групп: строка, переехавшая в другую группу,
  не перемонтируется, и открытая карточка не закрывается. Не возвращай `<section>` на группу.
- Сквозной сценарий — `e2e/roles.spec.ts`: роль модератора из UI, выдача из карточки, закрытый канал,
  удаление чужого сообщения, иерархия.

## Создание сервера

`/new` (`pages/new-workspace`, «+» в ленте серверов) — мастер `features/create-workspace` в три шага:
профиль (название, описание, аватар), шаблон стартовых каналов (`config/templates.ts`), права
участников. Шаги — одна форма RHF, поэтому «Назад» ничего не теряет. Отправка по порядку: `POST
/workspaces` → `PUT .../icon` → каналы шаблона по одному → переход в сервер. Ошибка на первом шаге
возвращает к полю, которое отклонил сервер; после него сервер уже есть, и сбой иконки или канала его не
теряет — сервер открывается, а `CreationNotice` говорит, чего не хватает (через `location.state`).
Голосовых каналов в шаблонах пока нет: шаблоны создают только текстовые.

Поля профиля и прав (`WorkspaceProfileFields`, `MemberPermissionsFields`) живут в `entities/workspace` и
работают внутри любого `FormProvider` — их же берёт экран настроек. Аватар обрезается по квадрату
в браузере (`shared/ui/image-cropper`, canvas, без библиотек) и уходит WebP или PNG 256×256; тип и
размер исходника проверяются на клиенте только ради подсказки, сервер проверяет байты сам. `iconUrl` —
подписанная ссылка на час: бери её из свежего ответа и не храни; битая ссылка — инициалы
(`WorkspaceAvatar`).

## Настройки сервера

`/s/:workspaceId/settings` (`pages/workspace-settings`, пункт «Настройки сервера» в меню сервера —
с правом `manageServer` или `manageRoles`; остальные и чужой сервер уводятся редиректом, хотя сервер всё
равно откажет). Каждый раздел виден только со своим правом. «Роли» (`manageRoles`, `RolesSettings` в
`features/edit-workspace`): список сверху вниз по старшинству, «Создать роль», стрелки порядка и редактор
(название, цвет, «показывать отдельно», права по группам). Менять и двигать можно только роли ниже своей
высшей, а включить — только право, которое есть у самого читателя (как проверяет сервер). Выдача ролей —
`MemberRoles` в карточке участника. Разделы: «Обзор»
(`features/edit-workspace`, `WorkspaceOverviewForm`: PATCH только изменённого текста, иконка — отдельно
`PUT`/`DELETE .../icon`), «Права участников» (`MemberPermissionsForm`, только изменённые флаги),
«Удаление сервера» (`features/delete-workspace`, только owner, подтверждение вводом названия, затем
`/`). Формы держат `values` из списка серверов с `keepDirtyValues`: чужая правка, пришедшая через
`workspace.updated`, появляется сама, а то, что человек сейчас печатает, не затирается.

### Профиль, аккаунт и статус

Вкладка «Профиль» (`features/user-card`: `ProfileSettings`, `ProfileFields`, `AvatarField`) — форма слева и
живая карточка справа; карточка — тот же `UserCardDetails`, что и везде, поэтому предпросмотр не копирует
разметку. Аватар обрезается по кругу (`shared/ui/image-cropper`) и уходит отдельным `PUT /users/me/avatar`,
удаление — `DELETE`; имя, «О себе» (счётчик до 190) и цвет акцента уходят одним PATCH только изменённым.
Пока вкладка грязная, уход с неё и закрытие диалога спрашивают подтверждение. Быстрый редактор из карточки и
панели использует те же поля и хук `useProfileEditor`: второй формы профиля быть не должно.

**Что публично.** `UserProfile` — это `nickname` (уникальный ник, не меняется здесь), `displayName`,
`avatarUrl`, `accentColor`, `bio`, `customStatus`, `isGuest` и `createdAt`. `email` и `profileOnboardedAt`
есть только в `SelfProfile` (`GET /auth/me`) и никогда не уходят другим. Профиль видят те, с кем у
читателя есть связь: общий сервер, общая беседа (в том числе личная) или дружба. Чужой, незнакомый или
заблокированный профиль отвечает **404**, а не 403, — по ответу нельзя перебирать аккаунты. В полном
профиле слот `ProfileTabsSlot` показывает «Общие серверы» и «Общие друзья» (FR-5, SCRUM-102); правила
видимости и поведение этих вкладок — в разделе «Друзья и видимость».

**Аватар.** Исходник выбирают в `AvatarField`, `ImageCropper` режет его по кругу в браузере (canvas, без
библиотек) и отдаёт WebP 256×256; сервер перекодирует картинку в WebP 256 и 64 px, срезает EXIF и
подписывает ссылку. `avatarUrl` — подписанная ссылка, её нельзя хранить; битая ссылка откатывается на
инициалы. Порог исходника (8 МБ, PNG/JPEG/WebP) проверяется на клиенте только ради подсказки — байты
проверяет сервер.

**`UserAvatar` — единственный способ показать человека.** Инициалы, цвет акцента, подпись для
скринридера и запасной вариант при битой ссылке живут в `entities/user/ui/UserAvatar`; не рисуй
`<span>` с первой буквой или `<img>` с `avatarUrl` руками. В `UserAvatar` передают профиль (или его
`nickname`/`displayName`/`avatarUrl`/`accentColor`), `status` — только там, где присутствие уже
известно, `decorative` — когда рядом есть текст с именем.

**Онбординг.** `SelfProfile.profileOnboardedAt` — единственный флаг шага «Заполните профиль»: `null` до
прохождения, дата после. Шаг (`ProfileOnboarding` в `features/user-card`, смонтирован в `widgets/app-shell`)
показывается, только пока флаг `null`; «Сохранить» и «Пропустить» отмечают его
`POST /users/me/onboarding` (204, идемпотентно; гость — 403). Источник истины — сервер и `GET /auth/me`,
поэтому шаг не повторяется и на другом устройстве; в `localStorage` флаг не дублируется. Закрытие
(Esc, крестик, фон) не отмечает шаг, но прячет его до конца этой сессии страницы — это память модуля, не
второй флаг. Гость шаг не видит: в своей карточке он читает «Зарегистрируйтесь, чтобы настроить профиль»
и получает `ClaimGuest`, а не форму, которая ответит 403. Если у полного аккаунта нет аватара, панель
пользователя показывает точку на аватаре и пункт «Добавить фото», ведущие во вкладку «Профиль».

Вкладка «Аккаунт» (`AccountSettings`) меняет ник и почту с текущим паролем и меняет сам пароль. Подсказки
говорят про две смены ника в час и семидневную задержку старого. Ошибки раскладываются по полям: 409 —
занятый ник или почта, 401 — неверный текущий пароль, 400 — валидация, 429 — лимит с `Retry-After`
(`ApiError.retryAfterSeconds`). Такие 401 не считаются концом сессии: у мутаций стоит
`meta.skipSessionExpiry`. Гость вместо форм видит объяснение и `ClaimGuest`; после создания аккаунта
настройки закрываются и открывается шаг профиля.

Статус меняется из меню панели пользователя пунктом «Задать статус» (`SetStatusDialog`): эмодзи, текст и
срок 30 минут / 4 часа / до конца дня / не сбрасывать. Ответ сервера кладётся в кеш через
`applyUserProfile`, как и аватар с профилем, поэтому лента и участники обновляются сразу.

### Сообщить о проблеме

Пункт «Сообщить о проблеме» внизу меню панели пользователя открывает `ReportBugDialog` (`features/user-card`:
слой `features` уже упирается в лимит Steiger в 20 слайсов, поэтому отдельного `report-bug` нет). Форма RHF:
«Что случилось» (обязательно, до 4000), «Как повторить» (до 4000) и скриншот — кнопка, файл или Ctrl+V;
PNG/JPEG/WebP до 5 МБ проверяются на клиенте только ради подсказки (`MAX_SCREENSHOT_BYTES` держите равным
`ORBIT_MAX_SCREENSHOT_BYTES` сервера). Окружение прикладывается само и показано в форме до отправки: версия
сборки (`build.version` из `@/shared/config`, `__APP_VERSION__` = версия пакета + коммит), браузер и система
(`getPlatform().system.describe()`), маршрут (`reportRoute`: только путь, код приглашения и id секретного
чата маскируются); аккаунт сервер берёт из сессии. Текст сообщений, токены и секретные чаты в отчёт не
кладём. Ошибки (`describeBugReportError`): 400 — к полю, которое назвал сервер, 413 и 415 — к скриншоту,
429 — над кнопкой с `Retry-After`. Сквозной смоук — `e2e/bug-report.spec.ts`.

## Друзья и видимость

**Где живут данные.** `entities/friend` — единственный владелец дружбы: `useFriends` (`GET /friends`, ник
и presence), `useFriendRequests('incoming' | 'outgoing')`, `useBlockedUsers`, `useFriendProfiles` (аватары
и статусы из профилей), действия `useFriendActions` (принять, отклонить, отменить, удалить,
заблокировать, разблокировать) и `useSendFriendRequest`. Списки и кнопки читают кеш TanStack Query, а не
локальный флаг: `friend.request.created/removed`, `friend.added`, `friend.removed` и `presence.updated`
гасят или точечно правят те же ключи (`friend.*` также гасит `getMutual`). Пока `listFriendRequests`
(`outgoing`) не покажет строку, интерфейс не утверждает, что заявка существует. Экран — `pages/direct`
(`FriendsPane`: «В сети», «Все», «Ожидание», «Заблокированные»), карточка человека — `features/user-card`.

**Кто что видит.** Онлайн-статус видят друзья и люди с общего сервера: `presence.updated` уходит в
серверы аккаунта и его друзьям, `GET /friends` и список участников отдают статус. С незнакомым человеком
точки присутствия нет; `dnd` считается «в сети», потому что сервер уже применил приватность и
невидимость. Публичный профиль и общие списки доступны только «знакомым»: общий сервер, общая беседа
(включая личную) или дружба. Иначе — **404**, не 403; пара с блоком в любую сторону тоже получает 404,
поэтому по ответу нельзя перебирать аккаунты. Гость не отправляет заявки и не начинает личные диалоги:
политика заявок (`all` / `shared` / `nobody`, по умолчанию `shared`) решает, дойдёт ли заявка, а блок
отменяет любую политику.

**Общие списки.** `GET /users/{userId}/mutual` — пересечение, а не объединение: серверы, где состоят оба
(с ролью вызывающего в каждом), и друзья, общие для обоих (полные профили). Себе — 400, посторонний,
неизвестный или заблокированный — 404. `useMutual` превращает 400 и 404 в `null`, поэтому вкладки
«Общие серверы» и «Общие друзья» (`ProfileTabsSlot` → `MutualTabs`) живут только в полном профиле и не
появляются для своей карточки ни при одном из этих ответов; в консоль ничего не пишется. Если оба списка
пусты, вкладок нет; если пуст один — внутри его вкладки пустое состояние. Клик по серверу ведёт в
`/s/{id}` и закрывает диалог; клик по общему другу открывает его профиль в том же диалоге (профиль уже
пришёл в `MutualOverview.friends`, поэтому лишнего запроса нет). Иконка сервера — подписанная ссылка из
ответа, её не хранят; битая откатывается на инициалы `WorkspaceAvatar`.

**Нейтральный ответ на заявку.** `POST /friends/requests` отвечает **202** и одинаковым телом на
сохранённую заявку, отказ по политике, блок и несуществующий ник. `AddFriendDialog` и `FriendActionSlot`
показывают одну фразу «Если такой пользователь есть, он получит заявку» и не меняют состояние по ответу:
заявка появляется в исходящих только тогда, когда её подтвердил сервер. Принять может только адресат
(иначе 404, как у несуществующей пары; полный список друзей — 409), а отклонение и отмена удаляют строку.

**Блокировка.** `FriendActionSlot` предлагает «Заблокировать» для любого чужого аккаунта: у друга — в
меню «Друзья» рядом с «Удалить из друзей», у не-друга — в меню «Ещё» рядом с текущим действием.
Подтверждения нет: блок обратим из «Заблокированных», как и блокировка из строки друга. После ответа
карточка закрывается, а состояние слота выводится из `useBlockedUsers`; пока карточка открыта, он
показывает «Заблокирован», а не предлагает действие снова. Себя заблокировать нельзя — слота на своей
карточке просто нет, сервер тоже ответит 400.

## Личные сообщения

**Маршруты.** `/me` открывает `pages/direct` (`FriendsPane` — друзья по умолчанию), `/me/friends` — тот же
экран, `/me/:conversationId` — беседа, `/me/s/:secretChatId` — секретный чат. Старые ссылки `/dm/*`
перенаправляются на `/me`. Беседа — это канал без сервера: сообщения, ответы, реакции, файлы и упоминания
идут через те же `widgets/channel-chat` и `features/*`, поэтому второго чата у личных сообщений нет.
Участники беседы приходят в `mentionPeople`, серверного `workspaceId` у неё нет.

**Список.** `DirectSidebar` читает `useConversationSummaries` (`GET /conversations?limit=20`,
`listConversationsInfiniteOptions`). Одна страница `ConversationPage` уже содержит всё для строки:
`lastMessage` (автор, текст, `kind`, `system`), `unread`, `mentions`, `lastReadSeq`, `members`, `name`.
Порядок задаёт сервер — живые беседы первыми; следующая страница берётся по `nextCursor`, когда читатель
доскроллил до конца (и кнопкой «Показать ещё»). Для пары имя — ник собеседника (`conversationPeer`), для
группы — её название или «Групповой чат» (`conversationName`); превью собирает `previewOf`: системная
строка — через `systemEventText`, вложение без текста — «Вложение», в группе перед текстом имя автора.
Поиск в колонке фильтрует уже загруженные строки, на сервер не ходит.

**Непрочитанные.** Их считает сервер по `lastReadSeq` каждой беседы и отдаёт в
`ConversationSummary.unread/mentions`; скрытые беседы в счёт не входят. Бейдж строки —
`UnreadBadge`/`describeUnread` из `entities/unread`, общий бейдж на рельсе — `useConversationUnreadTotal`
(`GET /conversations/unread`). `useReadOnView` двигает курсор (`POST /channels/{id}/read`) только когда
читатель внизу и вкладка видна; для лички он после успеха гасит `listConversations` и
`getConversationUnread`, а другие устройства узнают через личное `read.changed`. Свои сообщения не
считаются. Разделителя «Новые сообщения» в личке нет: всё, что пришло до открытия, — непрочитанное.

**Группы.** Создание — «Новый диалог» (`features/user-card`): один выбранный человек даёт пару, двое и
больше — группу; название необязательно и ставится отдельным `PATCH` (создание имени не знает). В группе
нет ролей: любой участник может переименовать (`PATCH /conversations/{id}`, 1–100 символов, 400 на пустое),
добавить людей (`POST .../members`; диалог «Добавить людей» предлагает только друзей) и выйти
(`DELETE .../members/me`, подтверждение в `LeaveGroupDialog`). Для пары те же действия отвечают **409**:
диалог не переименовывается, не растёт до группы и не «выходится» — его скрывают. Выход удаляет беседу из
списка и закрывает историю, файлы и live-поток; оставшиеся получают `conversation.updated` и системную
строку «X вышел». Добавление даёт новым `conversation.created`, остальным `conversation.updated` и по
строке «X добавил Y» на человека.

**Скрытие.** «Скрыть» в меню строки (`useHideConversation`, `POST /conversations/{id}/hidden`) убирает
беседу только у этого аккаунта и сразу из кеша; другим участникам ничего не приходит, системной строки
нет. Скрытие живёт до нового сообщения: сервер запоминает момент скрытия, и сообщение новее него
возвращает беседу в список само. Тост «Беседа скрыта» с «Вернуть» вызывает `DELETE .../hidden`
(`useUnhideConversation`). Другим устройствам аккаунта уходит личное `conversation.hidden`.

**Системные строки.** Сервер пишет их сам при изменении группы: `kind: 'system'`, `system.type` —
`member_added` (с `targetId`), `member_removed`, `conversation_renamed` (с `name`), а `content` — только
читаемый fallback. Рисуем по `system.type` через `systemEventText` (`entities/message`), а не по тексту
`content`: строки локализуются на клиенте, и превью в списке берёт тот же текст. У такой строки нет
автора-заголовка, действий, реакций и ответа; `startsNewGroup` всегда отделяет её от соседей. Новый
`systemType` сначала добавляется в `systemEventText`, иначе строка скажет «Чат изменился».

**Приватность и блокировки.** В настройках пользователя, вкладка «Приватность» (`features/user-card`):
`dm-policy` (`shared` по умолчанию, `friends`, `nobody`) решает, кто может начать новый диалог;
`friend-request-policy` (`all`, `shared` по умолчанию, `nobody`) — кто может отправить заявку. Это разные
настройки, и `nobody` не мешает писать в уже начатой переписке. Гость не начинает диалоги и не отправляет
заявки. Блокировка (`PUT/DELETE /users/me/blocks/{userId}`) отменяет заявку и дружбу и замораживает пару в
обе стороны: начать диалог и отправить сообщение нельзя, сервер отвечает **404**, а `DirectPage` показывает
«Пользователь недоступен — возможно, он ограничил переписку…» (нейтрально, без указания стороны). Своя
сторона видит «Вы заблокировали пользователя» и «Разблокировать». В общих группах история остаётся, но
сообщения заблокированного свёрнуты до «Показать». Чужой или заблокированный профиль — тоже 404.

**Уведомления и мьют.** `useDirectMessageNotifications` слушает личный `message.created` и показывает
системное уведомление «Личное сообщение» (клик ведёт в `/me/{id}`). В личке уведомляет каждое новое
сообщение, а не только упоминание; не уведомляет о своих и об открытой беседе в видимой вкладке. Режим
(все / только упоминания / выключены) — в `localStorage`; «Не беспокоить» (`dnd`) глушит всё. Отдельную
беседу можно замьютить из меню «Действия с диалогом» («Выключить/Включить уведомления»):
`setConversationMuted` хранит набор id в `localStorage` на этом устройстве, сервер о нём не знает.

## Приглашения и гости

Ссылку создаёт `features/manage-invites` из меню сервера или из шапки канала: кнопка видна с правом
`createInvite` (`can(membership, 'canInvite')`). Ссылка ведёт на
`/invite/:code` (`pages/invite`, маршрут вне `RequireSession`), где `GET .../preview` показывает
название сервера и число участников до всякой авторизации.

Вошедший аккаунт вступает одной кнопкой (`features/accept-invite`, `AcceptInvite`). Новый человек
вводит только имя: `GuestJoinForm` создаёт гостя, сессию и членство одним запросом, кладёт ответ в
кеш `useSession()` и уводит в сервер. Ссылки «Войти» и «Зарегистрироваться» несут `?next=` с путём
приглашения, а `useReturnPath` в `features/auth` возвращает туда после входа — только для путей
внутри приложения, `//host` отбрасывается.

Гость остаётся гостем, пока сам не захочет иначе: `features/claim-guest` на вкладке «Аккаунт» в
настройках пользователя показывает «Вы вошли как гость» и форму `POST /auth/claim`. Аккаунт сохраняет id, серверы, сообщения и историю;
после ответа обновляется только кеш сессии, и баннер исчезает. Список ссылок и отзыв — с правом
`manageServer`. Сервер отдаёт отозванные ссылки в общем списке, не помечая их, поэтому `ManageInvites`
держит отозванные этой сессией id отдельно и не показывает их; после перезагрузки они снова
появятся в списке, хотя ссылка уже мертва.

## Чат

`widgets/channel-chat` — история канала: виртуализованный список (`TanStack Virtual`), страницы по 50
сообщений назад по курсору `nextBefore`, порядок на экране — от старых к новым. Новое сообщение
прижимает список к низу только если читатель уже внизу; иначе появляется кнопка «К новым сообщениям».
Отправка — `features/send-message`: в теле идёт `clientMessageId`, поэтому повтор после обрыва даёт то
же сообщение, а не второе. Офлайн TanStack Query сам держит мутацию на паузе и отправляет её, когда
сеть вернулась, — композер говорит об этом, а не показывает ошибку. Оптимистичной вставки нет: источник
правды — история, её же освежает живое событие (`message.*` гасит и обычный, и infinite-ключ).
Группировку (имя и время один раз на серию) и подпись автора держит `entities/message`.

Упоминания, ответы, реакции, правка и удаление — `features/send-message` и `features/message-actions`.
`@` в композере открывает участников сервера (стрелки, Enter, Esc), ник вставляется в текст, а id
уходят в `mentions`: сервер сам текст не разбирает. Ответ несёт `replyToId`, превью в карточке
прокручивает к исходному сообщению, пока оно загружено. Реакция, правка и удаление возвращают
изменённое сообщение, и оно точечно кладётся в кеш истории (`replaceMessageInHistory`) вместо
перезапроса всей ленты. Живое событие всё равно помечает историю устаревшей — иначе чужие
изменения не доедут. Правка предлагается только автору, удаление — автору и тому, у кого в канале
есть `manageMessages` (`channelAllows` из `entities/channel`); удаление спрашивает подтверждение. По реакции сервер отдаёт лишь emoji, счётчик и «я среди них», поэтому подсказка
говорит «вы и ещё N», а не имена.

## Непрочитанные и уведомления

Счётчики — `entities/unread`: `GET /workspaces/{id}/unread` одним запросом на сервер. Сервер, за которым
следит поток, обновляется по событиям (`message.*` и личное `read.changed` гасят его ключ); остальные
серверы в ленте слева переспрашиваются раз в минуту — поток держит только один сервер. Отметка
прочитанного (`useReadOnView`) двигает курсор до последнего сообщения, когда читатель внизу ленты и
вкладка видна (`usePageVisible` из `shared/lib/page-visibility`); ответ сразу кладётся в кеш счётчиков,
а другие устройства узнают через `read.changed`. Разделитель «Новые сообщения» стоит там, где был
курсор при открытии канала, и не двигается, пока читатель в канале; свои сообщения его не ставят.

Уведомления — `features/notifications`: `useMessageNotifications` слушает `message.created` через
`useLive().listen` и показывает их только через `getPlatform().notifications`. Не уведомляем о своих
сообщениях и об открытом канале в видимой вкладке. Режим (все, только упоминания, выключены) хранится
на устройстве в `localStorage`; разрешение браузера спрашивается только по действию человека — при
выборе режима или по кнопке, никогда при загрузке.

Поля int64 (`seq`) в телах запросов уходят числами: генератор пишет `bigint` строкой, сервер такую
строку отклоняет, поэтому `bodySerializer` задан в `shared/api/client-config.ts`.

## Файлы

Показ — `entities/attachment`: превью изображений с размером, известным до загрузки (иначе
виртуальный список прыгает), просмотр в полном размере (Radix Dialog), остальные файлы — ссылкой
«Скачать». Ссылка подписанная и короткоживущая (`GET /attachments/{id}`, `useAttachmentLink`),
обновляется за минуту до истечения. Недоступное вложение (404 или картинка не грузится) показывает
заглушку, остальной список живёт дальше.

Загрузка — `features/attach-file`: кнопка, перетаскивание на чат и вставка из буфера; каждый файл
грузится сразу и отдельно, сообщение потом только называет их в `attachmentIds`, поэтому может уйти
без текста, но ждёт, пока догрузятся все файлы. Прогресс и отмена требуют XMLHttpRequest
(`uploadAttachmentWithProgress` в `shared/api`) — `fetch` прогресс отправки не отдаёт; это
единственный запрос, написанный руками. Лимит размера проверяется до отправки по
`VITE_MAX_UPLOAD_BYTES`: API его не сообщает, держите равным `ORBIT_MAX_UPLOAD_BYTES` сервера;
413 и 415 от сервера всё равно объясняются текстом.

## PWA

Манифест и иконки — `public/manifest.webmanifest` и `public/icons` (192/512, maskable, apple-touch).
`index.html` ссылается на манифест и `theme-color`; цвета взяты из `@theme`, но в hex: манифест не понимает
oklch.

`public/sw.js` — оболочка для установленного приложения. Навигация — network-first с откатом на
закэшированный `index.html`; хэшированные `/assets/*` и иконки — cache-first. При установке worker сам
читает собранный `index.html` и кладёт в кэш текущие хэши, поэтому офлайн открывается именно эта сборка.
API и WebSocket не кэшируются никогда. `Vary: Origin` у preview-сервера не должен ломать попадания:
`cache.match` вызывается с `ignoreVary`. Меняется схема кэша — поднимай `VERSION`, старые кэши удалит
`activate`.

Регистрация — `shared/pwa`, только в `import.meta.env.PROD`: в dev Vite отдаёт исходники, и worker
прятал бы изменения. Офлайн-проверка отдельная, потому что для неё нужен build и preview:
`pnpm test:e2e:pwa` (`playwright.pwa.config.ts`, порт 4173).

Установка — `features/install-app` через `PlatformAdapter.install`: браузерное событие
`beforeinstallprompt` приходит один раз и может прийти до рендера, поэтому адаптер держит его на уровне
модуля, а кнопка подписана через `useSyncExternalStore`. Без события (Safari, iOS) кнопки нет — там
приложение ставят через меню браузера.

## Медиа (LiveKit)

- Голосовой канал (`Channel.kind === 'voice'`) — постоянная комната LiveKit: имя комнаты — id канала,
  identity — id аккаунта. Клик по каналу в сайдбаре сразу подключает (`features/join-voice-channel`:
  `POST /channels/{id}/voice-token`), имя берётся из аккаунта, отдельной формы нет.
- `VoiceRoomProvider` живёт в `widgets/app-shell`, выше `<Outlet/>`: переход между текстовыми каналами
  и серверами не разрывает звук, а переход в другой голосовой канал пересоздаёт комнату и освобождает
  треки. Провайдер подключается лениво (`entities/voice-room/ui/LazyProvider`), чтобы livekit-client не
  попадал в начальный бандл.
- `VoicePanel` внизу колонки каналов — одна строка: цветной сигнал связи (текст в подсказке), «Голос
  подключён» и имя канала ссылкой, показ экрана и «Отключиться». Mute, deafen и громкость участника —
  в `UserPanel` и в карточке участника. Чужие демонстрации показывает `VoiceStage` над страницей канала.
- Страница голосового канала — сетка плиток участников (кольцо говорящего, значки mute/deafen/экран),
  демонстрации экрана крупно и кнопка «Подключиться», когда читатель ещё не в комнате. Клик по каналу в
  сайдбаре подключает и открывает эту страницу.
- Выбор микрофона и динамиков — `features/select-device`: списки через `PlatformAdapter.mediaDevices`
  (метки видны только после доступа к микрофону), переключение на лету — `room.switchActiveDevice`,
  динамики только там, где есть `setSinkId`; выбор и mute/deafen запоминаются в localStorage, пропавшее
  устройство откатывается на «По умолчанию» с тостом и подхватывается снова, когда вернётся. Уровень
  микрофона — анализатор LiveKit, проверка звука — короткий сигнал через платформу.
- Присутствие под каналом — `entities/voice-presence`: `GET /workspaces/{id}` отдаёт `voice`, а событие
  `voice.presence` точечно кладётся в кеш сервера. В активном канале список берётся из LiveKit (там есть
  говорящий), в остальных — из presence; mute и экран сервер обновляет вебхуками и небольшим опросом
  занятых комнат (`internal/voice`, SCRUM-35).
- Переподключение после потери сети делает сам LiveKit (resume, затем full reconnect, ~45 с) и сам
  переопубликует микрофон и экран; провайдер в это время отдаёт `status: 'reconnecting'`. Если LiveKit
  сдался — `status: 'disconnected'` и `connectionLoss`; `VoicePanel` показывает сообщение и кнопку
  «Переподключиться», которая просит свежий токен для того же канала. Офлайн в e2e — `context.setOffline()`.
- Mute, deafen и громкость участника — действия `useVoiceRoom()`. Deafen — громкость всех на 0 через
  `RemoteParticipant.setVolume()` плюс атрибут участника `deafened`. Индикатор говорящего — по
  `ActiveSpeakersChanged`, без опроса уровней; задержку задаёт `audio.update_interval` LiveKit
  (`deploy/livekit.yaml` в orbit-server).
- React Compiler считает ref-ом любое значение с суффиксом `Ref` и всё, что передаётся в проп `ref`: не возвращай из хуков
  объект с ref внутри, деструктурируй результат.

## Секретные чаты (SCRUM-82)

`entities/secret-session` — протокол: Olm (`@matrix-org/olm`, WASM) в Web Worker, ключи устройства,
сессии на чат, шифрование и расшифровка. Модуль грузится только вместе со страницей секретного чата
(`pages/secret-chat`, ленивый маршрут): открытие обычного канала не тянет WASM в начальный бандл.
`entities/secret-chat` — список чатов устройства и его публичная часть, без крипто-зависимостей.

- Аккаунт и сессии Olm хранятся pickles, зашифрованными AES-GCM ключом из IndexedDB через
  `PlatformAdapter.secretStore` (`web-secret-store.ts`). Ключ неэкспортируемый, `localStorage` не
  используется. Расшифрованные сообщения и отметки сверки — только в IndexedDB.
- Сервер видит публичные ключи, one-time pre-keys, конверты и метаданные. Никогда не отправляй текст,
  ключи, имена файлов в API, логи или события; отдельного API для истории секретного чата нет.
- `SecretSession` — единственное место, где живут `Olm.Account`/`Olm.Session`. UI не вызывает libolm
  напрямую; он вызывает методы сессии и перерисовывает `SecretChatView`.
- Смена ключа собеседника (`keyChanged`) сбрасывает «Проверено» и блокирует композер до повторной
  сверки кода безопасности. Не обходи это правило в UI.
- Таймер: локальное удаление из IndexedDB и `expiresAt` конверта/вложения на сервере; серверный TTL
  не больше недели. Не показывай уведомления с текстом — только «Новое сообщение в секретном чате».
- CSP и SRI собираются `scripts/security-html.ts` в `vite build`; `connect-src` включает origin API.
  Не добавляй сторонние скрипты и не ослабляй политику без security-ревью.
- Тесты: `src/entities/secret-session/model/session.test.ts` гоняет два устройства в одном процессе
  (обе стороны, перезапуск, replay, подмена ключа, вложения, пустой `localStorage`).
